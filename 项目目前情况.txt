# OrderMate 项目目前情况

更新日期：2026-08-02

## 一句话状态

OrderMate 现在已经从“普通电商后端 + 简单客服”推进到“Java 业务后端 + Python Agent + DeepSeek Function Calling + 本地完整演示链路”的阶段。当前重点不再是堆功能，而是把商品、购物车、订单这些真实业务动作做稳、做准、做得可演示。

## 当前整体架构

```text
浏览器前端
  -> FastAPI Agent 服务，端口 18000
  -> DeepSeek Chat Completions / Function Calling
  -> Python 工具执行层
  -> Java Spring Boot 业务 API，端口 8080
  -> MySQL 业务数据库
```

当前坚持的方向：

- Java API 保持为业务系统主体。
- Agent 不直接绕过业务规则写数据库。
- 结构化业务数据必须通过工具和 Java API 获取。
- RAG 暂缓，等 Function Calling 稳定后只用于售后、保修、规则、FAQ、产品手册等文档知识。

## 当前可用能力

### Java 商城后端

- Spring Boot 3.x 后端仍保留为核心业务 API。
- 已覆盖用户、商品、分类、购物车、订单、订单明细、地址等电商基础模块。
- 保留 JWT 鉴权和登录态能力。
- 购物车、订单等写操作继续由 Java API 执行业务规则。
- 本地演示数据已增强，包含适合测试价格、库存、分类、发布时间的商品。

### Python Agent 服务

- FastAPI 承载聊天接口和前端静态页面。
- 已接入 DeepSeek 兼容 Chat Completions 工具调用。
- 已处理 DeepSeek 工具调用时的特殊限制，避免 `reasoning_content` 与 tool call 冲突导致 400。
- 已修复多工具调用消息顺序问题，保证 assistant tool call 与 tool result 顺序合法。
- 已保留上下文状态，用于记录最近展示商品、购物车条目、订单、待确认动作等。

### Function Calling

当前重点工具包括：

| 工具 | 当前用途 |
| --- | --- |
| `search_products` | 查商品，支持关键词、分类、价格区间、库存、发布时间 |
| `get_product` | 查单个商品详情 |
| `get_cart` | 查看当前用户购物车 |
| `add_to_cart` | 添加商品到购物车 |
| `update_cart_item` | 修改购物车单项数量 |
| `remove_cart_item` | 删除购物车单项 |
| `get_orders` | 查询订单 |
| `create_order` | 创建订单，需确认 |
| `cancel_order` | 取消订单，需确认 |

内部还增加了确定性兜底逻辑，避免所有动作都交给模型猜：

- “把刚才那个红米手机加入购物车”可以从最近商品上下文解析商品。
- “把红米手机改成 2 件”可以从购物车上下文解析 cart item。
- “两个商品都改成 3 件”可以批量生成修改动作。
- “确认”“对”“可以”等自然语言会优先执行当前 pending confirmation。

### 购物车链路

已完成：

- 查看购物车。
- 基于最近商品上下文加入购物车。
- 单个商品数量修改。
- 多个商品批量数量修改。
- 写操作确认后再执行。
- 确认成功后清理待确认动作，避免重复执行。

仍建议继续优化：

- 前端应该把购物车结果渲染成稳定卡片，而不是纯 Markdown 表格。
- 确认卡应显示旧数量、新数量、商品名、动作类型。
- 失败时要展示真实业务错误，例如未登录、权限失效、条目不存在、库存不足。

### 商品查询链路

已支持的典型问题：

```text
4000以内手机
2026-07之后发布的耳机
价格100-300的充电宝
帮我找有库存的小米手机
```

商品查询必须走工具，不能让模型直接编造价格、库存、发布时间。

### 本地启动链路

当前推荐一行命令启动完整环境：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start-local-full.ps1
```

脚本负责：

- 设置 UTF-8 控制台。
- 检查 MySQL。
- 必要时使用 Docker Compose MySQL 兜底。
- 初始化数据库结构和演示数据。
- 启动 Java 后端。
- 启动 Agent 服务。
- 做健康检查。

停止命令：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\stop-local-full.ps1
```

## 当前风险与注意事项

### 1. 会话状态主要仍在 Agent 内存中

如果 Agent 服务重启，最近商品、购物车上下文、pending confirmation 可能丢失。后续如果要更接近生产环境，可以接 Redis 或数据库持久化。

### 2. 登录态可能失效

如果购物车、订单操作返回 401/403，优先在前端重新登录 demo 用户，再继续测试。

### 3. 模型仍可能偷懒

即使工具描述和 system prompt 已增强，DeepSeek 仍可能偶尔不调用工具。因此后端保留确定性兜底逻辑是必要的。

### 4. RAG 不应过早接入

当前最重要的是 Function Calling 稳定。RAG 如果现在和购物车、订单一起调试，会增加排查成本。

## 当前项目评价

这个项目目前已经具备比较清晰的企业项目落地逻辑：

- Java 后端负责真实业务。
- Agent 负责理解用户、调用工具、维护上下文。
- DeepSeek 负责生成工具调用和组织回答。
- MySQL 负责结构化事实。
- RAG 后续只补文档知识，不抢数据库查询的工作。

后续继续优化的关键不是“让回答更花哨”，而是让每一次查商品、改购物车、下单、取消订单都可追踪、可确认、可复现。
