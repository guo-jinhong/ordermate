## 1. 项目定位和用户目标

- 项目名称：OrderMate，电商智能客服演示系统。文件夹名称可以改变，不决定产品名称。
- 用途：求职 AI 应用开发、AI 全栈相关岗位时，作为项目经验和可操作的面试演示。
- 核心目标：让模型理解自然语言，通过真实业务工具查询和操作商品、购物车及订单；不把模型生成内容当成真实业务数据。
- 用户偏好：聚焦当前需求，直接修改必要代码，少空谈；消费者端文案自然、简短，不暴露内部参数和工具术语。
- 本项目主前端为 Vue，业务后端为 Java，Agent 为 Python。SportMate 是另外的微信小程序实习项目，不能混写技术栈或个人贡献。

- 普通聊天也开放匿名体验。

- 首页、侧栏、发送入口不再根据旧全局登录标记阻断公开聊天。

## 4. 已完成的 C 端话术调整

- 统一称呼用户为“您”。
- 商品卡片与演示回复日常展示“可购买 / 有货 / 暂时缺货 / 购买状态待确认”。
- 曾将 stock 总量写成“当前最多可购买”，复查后已修正：总量不等于实际操作上限，日常推荐和详情不展示该总量，也不编造每人、每单限购政策。
- 数量不足时，可说明目前可供购买的数量；真实业务数量限制仍由后端执行。
- 确认卡片清理“高风险”“将创建数据”“将删除数据”“目标数量”“影响范围”等后台表述。
- 下单、支付、取消订单、清空购物车需要服务端确认；普通加购、数量修改、移除直接执行并核实结果。
- 放弃确认使用“本次未操作”，按操作说明“您的订单未取消 / 本次未下单 / 本次未支付 / 购物车保持不变”。
- 演示支付成功明确提示不会真实扣款。
- 确认倒计时说明未确认不会自动操作；过期后禁止提交。
- 结果不确定时保留查看状态和不要重复提交的提醒，不伪装成成功或普通失败。
- 已将部分 Agent、工具参数、对象编号不一致等内部异常转换为消费者提示；不能据此断言所有异常都已完全分类。
- 加购后刷新完整购物车，刷新失败保留旧内容并阻止使用过期数量继续修改；连续操作保留滚动、展开和管理状态。这些部分来自此前前端聊天，后续已验证相关测试。

## 5. 已有的工程保护及边界

- 工具参数解析、意图校验、商品/购物车/订单对象对齐；对象不明确时澄清。
- POST / PUT / DELETE 等业务写请求不做 HTTP 自动重试；写回执丢失标记结果不确定，部分操作只读核实。
- 确认令牌默认 180 秒（本轮由 60 秒调整），绑定 session 和登录凭证指纹；一次性消费。确认及操作日志通过 SQLite 事务或 Redis CAS 防重。
- Java 根据认证身份取用户 ID，检查订单及地址归属。
- 下单有事务和商品悲观写锁，检查商品状态、数量、可用数量并扣减；单商品数量上限为 99。不要仅凭 stock 总量给用户宣称最大限购。
- 单次模型调用设置 20 秒超时；默认最大工具轮次为 5，可配置。已有模型熔断、接口限流、演示额度和并发限制。
- Redis 为可选能力；不能把“支持 Redis”直接说成所有并发、防重和限流状态都已经分布式化。
- SSE 当前通过事件展示处理进度及最终结果，不能凭“SSE”宣称模型文字逐 token 实时输出。

## 6. 本轮五项工程修复（2026-10-03）

以下是当前代码已实现的方式，不能再当作“仅提出建议”。真实 MySQL 容器验证仍待具备 Docker 服务的环境运行。

### 1. 阻止异常降级重放写操作

- 移除了 main.py 中 live Agent 异常后调用 demo Agent 重跑整条请求的路径。
- 无模型 Key 时启动选择 demo 的行为保留；备用模型切换只发生在模型调用内部。
- 写入后出错或总预算超时，提示先核实购物车/订单、不要重复提交。前端保留该提示。
- 回归覆盖故障发生在写入之后的情况，确认业务仅调用一次。

### 2. 合并读重试和耗时预算

- 工具注册表不再重试；HTTP 客户端统一处理读请求，默认最多 4 次尝试（首次 + 3 次重试）。
- READ_RETRY_BUDGET_SECONDS 默认 20 秒，包含当前 HTTP 读取和退避等待；读超预算停止继续尝试。
- CHAT_TIMEOUT_SECONDS 默认 60 秒，约束整段 Agent/确认执行，覆盖模型、工具和后续处理。鉴权及资源释放有独立边界，不把它描述成端到端网络严格 60 秒 SLA。
- POST/PUT/DELETE 不自动重试；结果不确定先只读查询。使用结构化错误标记，不再从客户话术猜测重试。
- SSE 断开时取消并等待执行任务释放资源；业务后端可能已经提交，不能把取消任务解释为业务回滚。

### 3. 下单业务幂等和操作结果持久化

- 确认快照落盘后才能返回确认卡片；服务端生成确认令牌，并把同一令牌作为该购买意图的 idempotency_key，客户端确认只提供 token 和批准/放弃。
- Java 下单事务：锁定用户行 → 查询 (user_id, idempotency_key) → 比较地址、支付方式、备注及商品数量的请求摘要 → 已存在则返回原订单 → 否则创建订单及扣减库存。
- MySQL Flyway V2__order_idempotency.sql 增加键、请求摘要和唯一索引。同键不同参数返回 409；旧客户端没传键仍兼容，因此不能声称所有外部手工下单都自动幂等。
- 操作日志保存 prepared / accepted / processing / executed / cancelled / failed / unknown。SQLite 写事务或 Redis CAS 原子占位；重复确认返回已保存结果，不重写。
- 本地默认 OPERATION_DB_PATH=agent_operations.db；Docker 基础配置为操作日志挂载独立数据卷。配置 Redis 时，操作记录共享在 Redis，Redis 重启后的恢复依赖持久化配置（AOF/RDB）及持久化卷。
- 订单回执丢失或业务提交后进程崩溃：按购买意图键只读查询真实订单；不把“看起来相似的新订单”当成本次订单。
- /operations/{token}?session_id=... 绑定会话与当前登录指纹，返回持久化结果或只读核实状态。前端确认网络异常时只查询该接口，查询仍失败展示待核实。
- 进程重启后可从已校验的持久化确认快照重建 LangGraph 审批节点；按钮与文字确认共享消费状态。
- 5 分钟内存重复提醒仍是用户体验辅助，不作为核心幂等保障。新确认令牌表示新的购买意图，不能保证判断出所有用户语义重复；也不宣称跨系统 exactly-once。

### 4. 摘要只记录已核实操作

- 不再用“取消、支付、下单”等关键词生成“操作记录”。
- 成功且有实际变更的工具结果、确认执行成功以及只读核实恢复成功，写入结构化 verified_actions。
- 咨询、待确认、取消本次操作、失败和未知结果不标记为已完成业务操作。
- 多次压缩保留已核实操作元数据；给模型的历史仍只含标准 role/content 字段，避免扩展字段进入模型接口。

### 5. 同会话并发和共享计数

- 聊天、SSE 执行、确认、结果查询及清理当前身份会话使用会话/身份互斥。同会话同时请求返回 409，不排队重放。
- Redis 模式使用带所有者的租期锁，租期至少 90 秒且大于执行预算；释放通过 Lua 比较所有者，进程退出后租期自动回收。释放失败不覆盖已经核实的业务结果。
- Redis 历史追加通过 Lua 原子完成；摘要压缩采用 CAS，避免压缩覆盖并发新增消息。
- Redis 会话状态完整保存待确认、购物车上下文和摘要字段，修复原来的字段遗漏。
- SlowAPI 使用配置的 REDIS_URL 共享接口限流。公网演示每日额度与在途请求数由 Lua 原子处理，使用请求租期回收崩溃占用。
- 未配置 Redis 的本地演示使用单进程互斥/计数；不把它称为多实例保护。生产配置校验原本已要求 Redis。
- Vite 与 Nginx 增加操作结果查询代理，避免新接口在前端落入 SPA fallback。

### 本轮明显错误复查补充（2026-10-03）

- HTTP 200 内的业务失败码不再被误判为成功；业务拒绝不自动重试。写请求返回业务 5xx 或格式异常时按结果不确定处理。
- 下单空回执、支付/取消错订单或空回执，进入只读核实；不能直接生成成功回执，也不会重发写请求。
- 清空会话会取消当前会话/登录身份的全部待确认快照；旧卡片再次确认返回 cancelled，不执行。已受理/执行的操作及其他用户、其他会话记录保留。
- 只读模式下文字确认被拒绝后持久化为 failed，避免遗留 accepted；共用确认执行入口再做只读检查。
- Redis 演示名额释放失败不覆盖业务结果，等待租期回收。SSE 在第一帧就断开也归还本地演示名额。
- 复查范围为当前工程化执行链路，不能把测试通过表述为覆盖所有真实环境故障。

### 建议确认后的逐项修复（2026-10-03）

- 用户已认可工程化建议并授权顺序修复；A—D 不再是待确认，E 确定保留旧接口兼容。计划及更新后的 16 道问答见 docs/工程化问答与待确认事项.md。
- 下单和取消/过期恢复数量统一按商品 ID 加锁；锁冲突返回 HTTP 409 和消费者提示，不自动重发订单写请求。同键不同参数的 HTTP 状态也修正为 409。
- 当前消息明确“再买/重新购买/再来一单”可跳过 5 分钟提醒，但必须生成新确认令牌；模型自报重复购买参数无效。相同登录指纹、商品和数量存在 accepted/processing/unknown 意图时先核实，不能用新会话绕过。
- 询问规则、假设场景、引用历史/引号中指令不构成本轮写操作授权；补充 live 校验和共用工具入口拦截及评测。关键词/正则仍有复杂语言边界，不声称完全理解自然语言。
- 未知确认卡片新增“核实操作结果”按钮，只 GET；失败保持 unknown，不再提交确认。下单按精确意图键恢复，支付/取消核对订单身份及状态后恢复；未执行占位的 accepted 支付/取消不因此归为成功。普通购物车操作仍通过查看/刷新核实。
- 确认默认 180 秒，可配置 CONFIRMATION_TTL_SECONDS；业务条件仍在执行时检查。
- 操作日志后台启动后每小时维护：executed/failed/cancelled 从完成/更新时间起保留 7 天；prepared 过期归档为 cancelled；accepted/processing/unknown 不自动删除。旧终态无时间戳时保守补时间再保留。OPERATION_RETENTION_DAYS 可配置。
- SQLite 写事务及 Redis CAS 保证清理不覆盖并发受理；订单表的意图键和唯一约束不随 Agent 日志删除，已删除令牌也不会再次获准执行。
- 应用测试默认操作日志使用独立临时 SQLite，修复固定假身份跨测试污染；没有清空开发操作数据库。
- 新增本机 MySQL 集成验证与启动脚本 scripts/run-engineering-mysql-check.py：创建唯一独立测试库，验证后只清理本次库。数据库测试采用真实 JPA 事务/锁/订单服务，购物车等依赖替换，不等于完整链路端到端验收。
