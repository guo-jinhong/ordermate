## 二、原 16 道问答，更新为当前实现

### 1. AI 会不会调用错工具？怎么防止？

答：有可能。工具定义和提示词之外，服务端检查用户意图、对象和数量；咨询取消规则不能直接当成取消指令，对象不唯一时澄清。Java 再检查权限和业务条件，不把模型输出当授权。

现状：已有保护，但部分意图判断依赖关键词和正则，不能保证理解所有复杂表达。

本轮补充：咨询、否定、引用历史及引号中指令的评测和入口拦截；改变主意、多对象的更广泛评测仍可继续扩充。现有“对象不清楚先问用户”规则已确定；具体歧义样例可以逐题讨论，无须重新决定是否允许猜测执行。

代码：agent-service/app/agent.py、agent-service/app/tools/registry.py。

### 2. 模型生成错误参数，是否直接执行？

答：参数先经 JSON 解析、类型、数量和对象一致性检查；关键业务规则仍由 Java 校验。错误或对象不明确时拒绝/澄清，不擅自换商品、订单或数量。订单写回执及异常后的核实回执都必须包含目标订单 ID，空回执、缺失 ID 或错订单进入待核实。

现状：已有实现，本轮无需改变规则。后续回归继续覆盖参数边界与错误回执；不宣称任意畸形参数都已穷尽。

代码：agent-service/app/tools/registry.py、agent-service/app/main.py、Java DTO 和服务层。

### 3. 工具超时后，会不会一直重试？

答：不会。已取消工具层重试，只由 HTTP 层处理 GET/HEAD/OPTIONS；默认最多尝试 4 次，含退避的读取预算 20 秒，超预算就停止。Agent/确认执行总预算默认 60 秒，不再存在原来两层叠加到 16 次的问题。

现状：原问题已修复。有多个独立读工具时，各自受读取预算限制，同时受 Agent 总预算约束。60 秒不包含所有鉴权、网络传输和清理时间，不能称为严格端到端 SLA。

后续调整：只有实际演示等待体验不合适时再调整超时数值，当前保持既定预算。

代码：agent-service/app/clients/ecommerce_client.py、agent-service/app/tools/registry.py、agent-service/app/main.py。

### 4. 数量不足、订单不能取消，也应该重试吗？

答：不应该。登录、权限、参数和业务条件拒绝直接反馈；可重试的是部分读请求网络故障和 HTTP 服务异常。HTTP 200 里的非成功业务码也会被识别，不会因为提示包含“暂时”而重试。

现状：已修正重试分类和业务码识别，使用结构化错误字段。写请求返回业务 5xx 或无法识别的回执时按结果未知处理，不能当成确定没写入。

待办：新增后端错误时同步错误映射即可；无需修改现有业务拒绝不重试的规则。

代码：agent-service/app/clients/ecommerce_client.py、agent-service/app/tools/registry.py。

### 5. 下单、支付或加购超时，能不能再发一次？

答：不能直接重发。POST/PUT/DELETE 不自动重试；超时和回执异常表示结果不确定，通过只读查询核实。订单创建按购买意图键查询；支付、取消核对目标订单状态，购物车操作查询购物车。仍不能核实时明确提示，不能报告成功或指导盲目重复提交。

现状：已实现。查询到状态也不能宣称所有购物车变化都能精确归因到本次请求；普通加购没有与下单同等的数据库意图幂等保障。

本轮已实施 B：未知确认卡片提供手动只读核实，不自动轮询；普通加购等直接操作仍通过购物车查看/刷新核实。复查已修正核实成功的清空空回执不刷新页面的问题；写结果未知时仅凭购物车为空仍保持未知。

代码：agent-service/app/main.py、agent-service/app/cart_operations.py、frontend/src/stores/chat.ts。

### 6. 禁止写重试后，为什么还可能重复加购？

答：之前异常降级会把整条请求交给演示代理重跑，第一次加购完成后再出错，第二次就可能再次加购。这个问题已复现并修复：运行时不再重跑业务，备用模型仅在模型调用内部切换。无 Key 时启动选择演示代理仍保留。

现状：写后异常返回已知结果或待核实，不因故障降级再执行原请求。已有写后故障回归；无需再选择是否允许降级重放。

代码：agent-service/app/main.py、agent-service/app/agent.py。

### 7. 高影响操作的确认，是不是只有前端弹窗？

答：不是。下单、支付、取消订单和清空购物车的动作及参数先保存为服务端快照，生成令牌并绑定会话、登录凭证指纹和有效期。确认请求只提交令牌及批准/放弃，不能临时替换参数；按钮和文字确认共享消费状态。

现状：普通加购、修改数量、移除直接执行并核实。清空会话撤销当前身份尚未确认的快照，旧卡片不能继续执行；已受理或已完成记录保留。

本轮已实施 C：默认 180 秒，可通过 CONFIRMATION_TTL_SECONDS 配置；有效期延长仍在实际执行时检查业务条件。

代码：agent-service/app/tools/confirmation.py、agent-service/app/operation_store.py、agent-service/app/main.py。

### 8. 连点两次确认，会不会下两次单？

答：同一令牌通过 SQLite 事务或 Redis CAS 原子消费和执行占位，重复确认返回已保存结果，不重复写入；处理中或未知也不能直接再次执行。前端确认响应丢失时查询 GET 操作状态，不再次发送确认 POST。Java 同一购买意图的防重再兜底。

现状：同一令牌防重已实现。新令牌属于新意图，不能把两个独立购买意图自动当成同一个。

本轮已实施 A：当前消息明确“再买/重新购买/再来一单”可生成新确认；咨询、引用或否定不授权；相同商品和数量有受理/处理中/未知意图时先核实。

代码：agent-service/app/operation_store.py、agent-service/app/tools/confirmation.py、frontend/src/stores/chat.ts。

### 9. 防重复下单，算完整幂等吗？

答：对同一用户、同一购买意图已实现业务幂等。服务端确认令牌作为意图键，Java 在事务内锁用户行、检查已有订单及请求摘要，再创建订单；数据库唯一约束兜底。同键同参数返回原订单，同键不同参数返回 409，不重复扣减数量。

现状：5 分钟进程内重复提醒只是体验辅助；不同会话或新令牌不保证语义去重，也不宣称跨系统 exactly-once。旧客户端不传键仍允许下单，因此不是所有外部调用都幂等。

A 已实施；E 已确定保留兼容。真实 MySQL 迁移、同意图并发及同键不同参数已验证。

代码：src/main/java/com/ecommerce/service/impl/OrderServiceImpl.java、src/main/resources/db/migration/V2__order_idempotency.sql。

### 10. 令牌已消费，服务突然崩溃怎么办？

答：已增加持久化操作日志：prepared、accepted、processing、executed、failed、cancelled、unknown。重启读取操作快照和结果；下单通过意图键只读核实真实订单。不能确认时保持未知，不能重新发写请求。持久化快照可用于重建审批节点。

现状：本地 SQLite，Docker 配置独立数据卷；Redis 模式共享记录，Redis 自身重启恢复依赖 AOF/RDB 和数据卷。存在持久化记录不等于所有故障都能自动确认结果。

B、D 已实施：终态从更新/完成时间保留 7 天，过期待确认归档；未知、已受理、处理中不删除。SQLite 重启已有自动化验证；真实 Redis 重启和数据卷恢复仍待验收。

代码：agent-service/app/operation_store.py、agent-service/app/main.py、docker-compose.yml。

### 11. 模型能查询其他用户的订单吗？

答：权限由后端决定。Java 从认证身份取用户 ID，并检查订单、地址归属；Agent 个人工具和确认要求登录，操作结果查询还绑定当前会话和凭证指纹。即使模型猜中别人的 ID，也不能越权查询或操作。

现状：公共聊天、商品推荐、规则咨询开放，个人订单、购物车和写操作登录。失效登录凭证仍拒绝，不当成已认证。

待确认：没有新的权限规则待定；现有规则继续保持。

代码：Java 控制器和业务服务、agent-service/app/main.py、agent-service/app/tools/registry.py。

### 12. 并发下单会不会超卖？

答：Java 下单有事务，锁定商品后检查和扣减可用数量；失败通过事务回滚。保护可用数量与判断重复购买是两件事，前者由商品锁及事务处理，后者由意图键和唯一约束处理。

现状：本轮下单和取消/过期释放统一按商品 ID 加锁，减少逆序循环等待；锁冲突通过 HTTP 409 反馈，不自动重放写入。不应宣称所有并发场景都已验收。

已验证：真实 MySQL 多用户逆序购买、同意图并发、唯一索引及事务回滚；Java 单元回归覆盖取消释放的锁顺序。更复杂并发压力和故障矩阵仍未穷尽。

代码：src/main/java/com/ecommerce/service/impl/OrderServiceImpl.java。

### 13. 两个页面同时聊天，会不会串上下文？

答：按身份及会话隔离；同一身份会话的聊天、SSE 执行、确认、结果查询和清理互斥，重叠请求返回 409。Redis 使用带所有者的租期锁，历史通过 Lua 原子追加，摘要通过 CAS 避免覆盖新消息。

现状：未配置 Redis 时仅提供单进程保护；配置后才能跨实例共享。不同 session 是独立会话，不保证互相排队。锁有租期，不宣称无限长停顿下仍绝对互斥。

待验证：真实 Redis、多进程并发及实例异常退出。当前无需为本地面试演示强制引入更复杂的排队系统。

代码：agent-service/app/reliability.py、agent-service/app/redis_stores.py、agent-service/app/main.py。

### 14. 摘要会把咨询当成已完成操作吗？

答：原来用取消、支付、下单关键词生成操作记录，确实会误记，已修复。现在操作记录来自已核实的成功工具结果、确认执行结果或只读恢复结果，写入 verified_actions；规则咨询、待确认、失败和未知结果不记成已完成。

现状：多次压缩保留已核实元数据，模型历史只传标准 role/content。摘要用于上下文，不取代数据库真实订单或购物车。

待确认：无需改变规则；新增操作类型要同步其核实条件。

代码：agent-service/app/conversation_memory.py、agent-service/app/tools/registry.py、agent-service/app/main.py。

### 15. 超时、熔断、限流都有了，能稳定部署吗？

答：已有单次模型 20 秒超时、最大工具轮次默认 5、Agent/确认 60 秒预算、模型熔断、接口限流和演示额度。Redis 模式共享限流、每日额度和在途租期，异常退出占用可回收；清理失败不覆盖业务结果。SSE 断开取消 Agent 任务，但不等于已提交业务回滚。

现状：这些是工程基础，不能据此宣称已生产验收。SSE 当前展示处理进度和最终结果，也不是逐 token 输出。

验证情况：真实 MySQL 迁移、同意图并发、逆序多商品下单及事务回滚已通过；真实 Redis 持久化、多实例故障及浏览器端到端仍待验收。容量、延迟和恢复指标没有实测，不编造生产规模与 SLA。

代码：agent-service/app/main.py、agent-service/app/reliability.py、agent-service/app/config.py。

### 16. 这个项目实际解决了什么问题？

答：我把自然语言客服接入商品、购物车和订单业务。模型理解需求并选择工具，服务端校验意图、对象及确认快照，Java 负责认证、归属、事务和状态规则。对写请求区分失败与结果未知，避免盲目重试；对同一购买意图落实业务幂等，对确认及结果持久化，支持异常后的只读核实；摘要和会话并发也有相应保护。

现状：这是具备工程保护的面试演示项目，不能称为真实支付、完整退货退款闭环或已经生产验证的系统。个人职责应按实际贡献口述，不把所有仓库能力自动算作自己独立开发。

待确认：若要制作个人面试口述版本，再由用户确认自己负责的模块和贡献；本轮不编造职责、上线效果或规模。
